# Дизайн-система Supplyo

## Поля

Общий контракт находится в `src/styles/controls.css`. Компоненты `Input`,
`SelectTrigger` и `EditableStockValue` подключают его атрибутом `data-ui-control`.
Новые поля должны использовать эти компоненты, без локальных цветов и focus-правил.

- Скругление: `--control-radius`, 8 px.
- Высота: 36 px; компактная ячейка таблицы — 32 px.
- Горизонтальные отступы: 12 px с обеих сторон.
- Иконка: отдельный промежуток 8 px; в поиске слева зарезервировано место для неё.
- Фон: `--secondary`; наведение: `--accent`.
- Наведение и фокус: одинаковая внутренняя обводка, без изменения размеров.
- Ошибка: `--destructive`; disabled: 50% прозрачности.
- Поиск отличается только размещением иконки. Редактор ячейки сохраняет геометрию.

## Статусы и действия

`SuccessBadge` переиспользуется для «Готов» и «Отгружена»: зелёная заливка,
белая галочка и текст. Интерактивный статус «На сборке» использует основной `Button`.
Не оформлять обычные статусы как кнопки.

## Таблицы

Использовать общие `Table` и `Card`. Пустой `CardFooter` не выводить.
Панель под таблицей допустима только с действиями или содержимым.

## Общие правила

Без декоративных стрелок. У контролов равные внешние отступы; иконки не должны
перекрывать текст. Экранные стили отвечают за размещение, компоненты — за состояния.

## Выбор кабинетов

`CabinetPicker` поддерживает несколько кабинетов и пункт «Выбрать все».
Частичный выбор показывает промежуточное состояние чекбокса; меню остаётся
открытым при переключении. Разделители меню используют `--separator-color`: цвет текста с 10% непрозрачности поверх фона, без сплошной тёмной заливки.
Данные и сводки агрегируются по выбранным кабинетам. Операции добавления в
поставку требуют заказов одного кабинета, чтобы не смешивать их данные.

## Уведомления

`src/styles/notifications.css` задаёт общий синий акцент для информации,
загрузки и подтверждения действий. Ошибки используют красный `--destructive`.
Текст и иконки контрастные, скругление берётся из общего `--control-radius`.

## Сетки карточек

Единственная карточка в overview-grid, warehouse-grid, metric-grid, account-grid
и account-warehouse-grid занимает все колонки. Несколько карточек используют
обычную адаптивную сетку. Не оставлять пустую колонку рядом с одиночным блоком.

Страницы и одиночные секции, включая профиль и формы организации, используют
всю ширину main. Не задавать им фиксированный max-width и центрирующие поля.
Ограничения ширины допустимы для отдельных контролов и диалогов.

Деструктивные действия: `Button` с `data-intent="destructive"` для иконок
или `variant="destructive"` для подтверждения. Hover и клавиатурный фокус:
красная внутренняя обводка и белая иконка, без синей заливки.

`MultiSelectPicker` — общий компонент выбора с чекбоксами для кабинетов и складов.
Цвет фокуса в тёмной теме: `--portal-focus: var(--portal-primary)`; фиолетовые
оттенки фокуса не использовать. Учёт агрегируется по отмеченным складам;
новая запись требует выбора одного склада.

Вторичный текст: `--text-secondary` (#a1a1aa в тёмной теме). Описания и
вспомогательные подписи используют общий токен через portal-subtle/portal-muted.

## Загрузка

`Skeleton` — единый анимированный плейсхолдер с нейтральными полупрозрачными
токенами. `LoadingBoundary` показывает его через 150 мс загрузки, сохраняя
смонтированные формы и геометрию блока. Скрытые контролы получают inert.
Область объявляет aria-busy и одно сообщение о загрузке; отдельные полоски
скрыты от скринридеров. Анимация отключается при prefers-reduced-motion.

`PageSkeleton` содержит композиции обзора, таблиц, профиля, складов, настроек
и учёта. Lazy-разделы используют Suspense и DeferredPageSkeleton.
Реальные асинхронные операции (обновление, проверка принтеров, загрузка
документов) используют LoadingBoundary. Для синхронных локальных данных
не создавать искусственную задержку ради демонстрации скелетона.

## Сортировка таблиц

`TableSortMenu` — заголовок с функциональной иконкой и радиопунктами Dropdown Menu.
`aria-sort` находится на ячейке заголовка. Для статусов доступны приоритет ошибок,
готовые первыми и сброс к естественному порядку адресов. Одинаковые статусы
сохраняют порядок по адресу и ID; сортировка не меняет исходные данные.

Проверка сортировки: `node --test tests/order-sorting.test.ts` (Node.js с поддержкой TypeScript).
