# Контекст Supplyo для продолжения работы в новом чате

Состояние на 10 ноября 2026 года. Это передача контекста разработки сайта Supplyo, ранее называвшегося «ЗакупИТ — WMS v2». Ниже отдельно указаны действующие требования, реализованные изменения и границы проверки. Продолжать нужно существующую новую серверную версию с сохранением данных и дизайна.

## 1. Цель продукта и текущая задача

Supplyo — ВМС для продавцов маркетплейсов, фулфилментов и их сотрудников. Полный путь: посадочная страница → регистрация/вход → подключение своего магазина или покупка подписки → настройка склада/сотрудников → подключение клиентов по коду → новые заказы → поставка → сканирование, КИЗ и печать → передача в доставку → учёт работ, зарплаты и финансов.

Пользователь просит рабочий сайт на сервере, доступный с другого компьютера, а не очередной макет. Покупка подписки сейчас намеренно имитируется без списания денег; запросы к WB и операции с его заказами настоящие. Нельзя называть имитацию реальным платежом или выдавать неподключённую интеграцию за работающую.

Последняя выполненная задача перед переносом: **подключён раздел «Остатки», проверен и опубликован на сервере**. Текущая задача — сохранить весь контекст для нового чата. Новую функцию сверх этого запроса начинать автоматически не нужно.

Пароли хешируются scrypt с индивидуальной солью. Серверные сессии — HttpOnly cookie, на HTTPS Secure. Есть проверки Origin/клиентского заголовка и ограничения попыток входа. Вложения — записи bytea с проверкой владельца; в опубликованной документации лимиты 5 MiB на файл, 100 MiB на аккаунт, Nginx request body 6 MiB. ## 5. Роли и доступы — самые важные правила

Нет взаимоисключающего глобального признака «это только клиент» или «это только фф». Один пользователь может иметь собственные API-магазины, подключённые клиентские кабинеты и доступ как сотрудник. Интерфейс и сервер определяют разрешённые действия по конкретным связям, складам, правам и подписке.

Не выводить роль из email, ФИО или одного факта добавления API/кода. Несколько собственных API также не делают аккаунт автоматически фулфилментом с доступом ко всему.

| Контекст | Разрешения |
| --- | --- |
| Новый клиент без подписки | Профиль/настройки, подключение своего API, выдача доступа к одному складу фф, обзор связанных складов. Самостоятельная ВМС закрыта. |
| Аккаунт с активной подпиской | Собственная ВМС в рамках тарифа, физические склады/сотрудники/учёт, подключение клиентов по коду. |
| Фулфилмент по активному доступу | Только конкретный кабинет и WB-склад, которые выдал клиент. API владельца не раскрывается. |
| Сотрудник | Только назначенные физические склады и связанные с ними кабинеты, только выданные права. Своя платная подписка не нужна, нужна активная подписка работодателя. |

**Актуальное решение: свой API можно добавить БЕЗ покупки подписки.** Раннее обратное пожелание отменено. Это не открывает неоплаченному владельцу все заказы, сборку или учёт.

Неоплаченному пользователю показывается привычная навигация, но недоступные разделы неактивны, с понятным tooltip о подписке. Подключение магазина и выдача доступа остаются доступны. Права проверяются сервером на каждом запросе, а не только disabled-кнопкой.

Удаление сотрудника, изменение его прав, отзыв доступа или окончание подписки работодателя должны реально отнимать доступ. Сотрудник не может сам расширить свои права, привязки складов, увидеть бухгалтерию владельца или посторонние кабинеты.

Адреса из тестов/скриншотов отличаются одной-двумя буквами — не путать:

- `[private-email-redacted]` — использовался как владелец фулфилмента;
- `[private-email-redacted]` — клиент без подписки;
- `[private-email-redacted]` — сотрудник.

Это контекст тестирования, не основание жёстко прописывать роли в коде.

## 6. Свои магазины, коды и подключение клиентов

Магазин WB подключается персональным API-ключом. Название продавца/ИП/ООО берётся из WB, не вводится вручную. Для Ozon нужны и API-ключ, и Client ID; оба должны иметь действие редактирования. **Реальная интеграция нового сервера подтверждена для WB FBS; наличие Ozon в прототипе не означает готовый live Ozon.**

Карточки подключённых магазинов: название, маркетплейс, статус, замаскированный ключ, Client ID для Ozon. Карандаши справа у соответствующего поля, компактные интервалы; подсветка редактируемых строк отдельно, а не всего внешнего блока. Не показывать чужому тестовому аккаунту вымышленные «подключённые магазины». Кнопка «Скрыть примеры» пользователем удалена.

Сценарий делегирования:

1. Клиент подключает свой магазин и подтверждает ключ.
2. В «Настройки → Доступ фулфилменту» выбирает подключённый кабинет и **один WB-склад**.
3. Создаёт одноразовый код. В текущей реализации код действует 24 часа, хранится digest, полный код возвращается один раз.
4. Передаёт код владельцу фф самостоятельно. Автоматическое письмо-приглашение не реализовано и не должно обещаться.
5. ФФ с активной подпиской открывает «Настройки → Клиенты», вводит **только код**. Email и выбор маркетплейса здесь лишние и удалены: сведения уже определены кодом.
6. Сервер атомарно проверяет срок, одноразовость, лимит кабинетов и создаёт доступ к выбранному складу. Повторная активация не должна создавать дубли.
7. ФФ связывает этот доступ со своим физическим складом для сотрудников и отображения имени.

Несколько складских доступов одного клиентского кабинета учитываются как один кабинет при проверке лимита. Новый код заменяет старые неиспользованные коды той же пары, но не отзывает уже принятые подключения. Клиент может отозвать принятый доступ, фф — отключить клиента. В истории владельца отозванные связи сохраняются.

Delegated route ID — это ID grant, не ID владельца магазина. Сервер сам разрешает реальный магазин и ограничивает склад. Нельзя доверять переданному браузером произвольному storeId/warehouseId.

Исторический текст «Ожидает проверки кода» был заглушкой, вызвал вопрос пользователя; он не заменяет настоящую активацию. Хинт про доступ должен содержать только: **«Доступ можно отозвать в любой момент.»**

## 8. Обзор при нажатии на логотип

**Логотип всегда ведёт на дашборд**, в том числе у клиента без подписки. Раннее перенаправление пустого аккаунта в настройки было отменено. Пустой обзор — нейтральное состояние, без навязчивого приглашения «выдать доступ».

- Неоплаченный владелец магазина видит свои WB-склады, к которым уже подключён фф с действующей подпиской. Не pending-коды и не все склады кабинета.
- Платный владелец/фф видит свои разрешённые складские области и входящие подключения клиентов.
- Сотрудник видит только назначенные области с правом просмотра.
- Счётчики: новые заказы, на сборке, готово из общего количества, передано в доставку. Данные берутся из БД без WB-запроса на каждое открытие.
- В карточке клиента «Фулфилмент: …» — **название физического склада, которое ввёл фф**, а не ФИО зарегистрированного человека.
- У фф и сотрудника не выводить бессмысленное «Фулфилмент:» про себя, пустую подпись или клиентский заголовок «Ваши склады у фулфилментов».
- При неоднозначном сопоставлении имя не подставлять наугад.

Справочник WB-складов сохраняется, чтобы отображались и разрешённые склады без заказов. Удалённая когда-то демонстрационная карточка Москвы не означает запрет показывать настоящую Москву, если к ней есть корректный доступ.

## 9. Физические склады и сотрудники

Это отдельная сущность от склада продавца в WB. ФФ создаёт свой физический склад: название, город, адрес, сотрудники. Связи «Кабинеты склада» определяют, с какими WB-складами могут работать его сотрудники.

Интерфейс согласован такой:

- Три карточки склада в ряд на широком экране, адаптация на узком.
- Название и город сверху, тонкая линия между городом и адресом.
- Редактирование адреса — карандаш справа в строке адреса, меняется только адрес.
- Удаление склада — крестик справа сверху, правильно выровненный.
- Общая нижняя кнопка «Редактировать» удалена. Серая полоса окончания карточки остаётся без лишнего текста.
- «Добавить сотрудника», затем вертикальный список сотрудников: ФИО сверху, email ниже, удаление справа.
- Вся подложка сотрудника подсвечивается серым при наведении, как строка ВМС; действие удаления дополнительно различимо.
- При одном складе показываются ещё две серые карточки «Добавить склад». Следующая активна, следующая за ней неактивна до заполнения предыдущей. Дублирующая верхняя кнопка добавления удалена.

Добавление сотрудника: ФИО + email, затем отдельные разрешения:

1. Просмотр заказов и остатков.
2. Сборка, КИЗ и печать этикеток.
3. Создание поставок и передача в доставку.
4. Изменение остатков, ячеек и адресов.
5. Управление складом и сотрудниками.

Кнопки пресетов «Просмотр / Сборщик / Администратор» пользователь удалил. Подпись «Просмотр» под каждым сотрудником тоже удалена. В существующей карточке сотрудника ФИО/email сначала readonly, редактируются по карандашу. При открытии диалога не должно самопроизвольно выделяться ФИО.

Сотрудник должен зарегистрироваться и войти **с тем же email**. Добавление записи не создаёт автоматически учётную запись и не отправляет письмо. Изменения доступа подтягиваются опросом сервера.

Критический исправленный баг: при добавлении фф второго клиента у сотрудника пропадали все кабинеты. Для legacy-случая с одним физическим складом теперь сохраняются все действующие делегированные области. Собственные новые магазины не выдаются автоматически. Явные bindings имеют приоритет, **даже если список пуст**. Для нескольких физических складов нужны явные привязки; неоднозначность должна закрывать доступ, а не открывать всё.

## 10. Новые заказы и создание поставок

Новые заказы:

- Чекбокс каждого заказа и выбор всех показанных одной кнопкой/чекбоксом.
- Номер заказа — первый информационный столбец; далее товар/размер, ячейка и адрес, все баркоды, дата/время последним столбцом.
- Статус в новых заказах удалён. **Стикера до создания поставки нет**, колонку не показывать.
- Поиск по номеру/артикулу/названию/баркоду/размещению в пределах доступных данных.
- «Добавить в поставку» и «Создать поставку (N)» видны постоянно. Первая неактивна, если нет подходящей открытой поставки/выбора. Не скрывать её, из-за чего прыгает панель.
- Если уже есть подходящая открытая поставка того же кабинета и склада, можно добавить заказы в неё; если несколько — выбрать. Не предлагать только создание новой.
- Сервер проверяет свежесть новых заказов, принадлежность складу, совместимость доставки, отсутствие дублей и закрытость поставки.
- Одна поставка — **один склад**, «Все склады» внутри неё недопустимо.
- Добавление новых заказов не стирает результаты сборки существующих.

В ВМС фф по одному клиентскому grant нет выбора чужих городов/складов: область уже выдана клиентом. Для собственных магазинов с несколькими разрешёнными складами выбор нужен. Не смешивать это со складом назначения СЦ/ПВЗ.

## 11. Сборка и ввод сканера

В сборке после статуса идёт отдельный номер заказа, затем товар, размещение, баркоды, стикер/действия в соответствии с доступными данными. Вместо ручной кнопки «Собрано» — «КИЗ» при необходимости и «Печать».

Поле сканирования отдельно от поиска. Кнопку «Сканировать» и пояснение «Сканер вводит код сюда. Поиск в таблице работает отдельно» пользователь удалил. Сканер сам передаёт Enter; при ручном вводе Enter нажимает человек.

Если фокус не в другом редактируемом поле и человек начинает печатать/сканировать, ввод направляется в сканер. Нельзя перехватывать ввод в поиске, диалоге КИЗ, профиле и других формах. Пустое поле поиска, в которое ничего не ввели **4 секунды**, теряет фокус, чтобы следующий скан попал в сканер. Не возвращать старые 3 секунды.

Любой баркод товара должен находить его, включая дополнительные. Сообщение для неизвестного кода: **«Нет такого баркода»** или «Баркод не найден», а не «Ошибка: другой товар».

Статусы оформлены цветными компактными badge:

| Статус | Вид |
| --- | --- |
| Ожидает | Жёлтый/янтарный |
| Проверяется | Фиолетовый, индикатор ожидания |
| Готов | Зелёный, галочка |
| Ошибка / Ошибка КИЗ | Красный |

Справа у панели поиска показывать **«Собрано X из Y»**, выровненное с остальными контролами. Счётчик готовности и возможность передачи учитывают всю поставку, не только отфильтрованные строки.

## 12. Как определяется необходимость КИЗ

**По API WB, не ручной галочкой оператора.** Последний обнаруженный реальный случай: WB вернул `requiredMeta: []`, но `optionalMeta: ["sgtin", "customs_declaration"]`. Проверка только requiredMeta пропустила КИЗ.

Теперь единое правило на frontend и backend проверяет **обе коллекции — requiredMeta и optionalMeta** на наличие `sgtin`. При неизвестных требованиях заказ нельзя считать немаркированным: запретить автоматическую готовность, Auto и преждевременную доставку.

Регрессионный пример: заказ `6240319070`, поставка `WB-GI-308031447`, магазин Гагарина, товар «защипбордов». Ранее он ошибочно стал готовым без КИЗ. Добавлено восстановление ошибочного Ready для открытых маркированных поставок при старте; уже сохранённые этикетки и квитанции печати не стираются. Закрытую историю не переписывать.

Положительный ответ WB о проверке КИЗ обязателен. Состояния вроде `filled` или `optional` **сами по себе не подтверждают корректность маркировки**.

## 13. КИЗ и готовность заказа

Правильная последовательность:

1. Сканируется баркод, определяется заказ и требование КИЗ.
2. Если КИЗ нужен, вводится/сканируется маркировка; проверяется структура.
3. После структурно корректного КИЗ **стикер печатается сразу**, без ожидания завершения проверки WB и без дополнительного окна предпросмотра.
4. Передача/проверка КИЗ в WB выполняется асинхронно.
5. Заказ остаётся «Проверяется», пока WB не подтвердил КИЗ.
6. «Готов» разрешён только при двух условиях: успешное подтверждение печатного задания и положительное решение WB по КИЗ.
7. Отрицательный ответ WB → «Ошибка КИЗ»; проблема печати → соответствующая ошибка/повтор, без обхода проверки.

Для заказа без КИЗ готовность определяется успешным выполнением печатного сценария. Неизвестные требования не равны отсутствию КИЗ. Прямой/повторный acknowledgement не должен превращать маркированный заказ в Ready без положительной проверки.

Поле КИЗ принимает корректные структуры маркировки, включая разные допустимые длины/форматы. Обычный EAN или случайный текст должен дать понятное «Отсканируйте КИЗ». Не сводить проверку к одной длине.

### Разделители и русская раскладка

Точный пример от пользователя:

```text
[Customer marking-code example omitted from public repository. See isolated scanner tests.]
```

Нужно преобразовывать физические клавиши сканера в US English, включая регистр и Shift-пунктуацию; вставленная русская строка тоже нормализуется. Это не обычная транслитерация текста. Поиск и обычные текстовые формы сохраняют русский язык.

F8 / Ctrl+] дают GS `U+001D`. Для проверенной структуры GS1 с AI 91/92/93 отсутствующие разделители или одиночные пробелы границ, которые показывает телефон, восстанавливаются в GS перед сохранением/отправкой. Нельзя просто удалять все пробелы или менять серийный/криптографический хвост. Исправление формата не гарантирует, что WB примет КИЗ с действительно неподходящим бизнес-статусом.

Эти изменения уже внесены и прошли серверные и браузерные регрессии с точной строкой пользователя.

## 14. Печать и режим Авто

Печать — реальные этикетки WB через **локальный Windows-агент**, не `window.print()` всей страницы. В истории ошибка печатала 16 страниц текста сайта — такое недопустимо.

Агент перечисляет принтеры Windows, сайт предлагает выбрать из списка, выбор сохраняется для браузера/рабочего места. Сервер в дата-центре не может сам увидеть USB-принтер сотрудника.

«Найти принтеры», выбор принтера и скачивание агента находятся в **Настройки → Печать этикеток**, не в панели сборки. Исходники: `public/print-agent/start-agent.cmd`, `wb-print-agent.ps1`, архив `public/supplyo-print-agent.zip`.

Раньше пользователь запускал CMD прямо из архива, не находился PS1; затем Windows блокировала неподписанный PS1. Не решать это глобальным отключением политики безопасности без необходимости. При изменении агента обновить также ZIP и проверить реальный состав архива.

Переключатель **«Авто»** по умолчанию выключен. Включённый режим:

1. Один скан баркода выбирает все ещё неготовые/ненапечатанные заказы этого товара **только в выбранной поставке**.
2. В набор входят лишь заказы, для которых явно установлено отсутствие КИЗ. Заказы с КИЗ и неизвестными требованиями исключаются.
3. Сначала полностью подготовить все необходимые стикеры. WB запрашивается пачками до 100 order ID.
4. Сохранить неизменяемый manifest с устойчивым job ID.
5. Отправить агенту **один `/print-batch` со всеми этикетками**. Агент сначала загружает изображения и отправляет единый Windows PrintDocument.
6. После общего idempotent acknowledgement обновить статусы пакета.

Это заменяет старое поведение «напечатал две, остановился, ещё одну, остановился». Нельзя реализовать Auto циклом отдельных независимых print job.

Повтор Enter/ошибка подтверждения не создают повторную печать. При повторе незавершённого намерения сохраняются job ID, файлы и принтер. При **намеренной новой индивидуальной печати** нужен новый случайный job ID: раньше повторные печати подавлялись dedup-логикой агента. Для повторной печати закрытой поставки есть отдельное подтверждение и новый ID.

Приём задания очередью не доказывает выход бумаги. Уведомления должны различать подготовку, передачу агенту, уже принятый дубль, подтверждение и ошибку. Не обещать «напечатано», если подтверждён только запрос.

Уведомления справа снизу, как в макете: обновление, подготовка, печать, завершение, ошибки. Они уже восстановлены в live-версии.

## 15. Передача в доставку и этикетки коробов

Нижняя панель появляется только когда **все** заказы поставки готовы. Слева переключатель «В СЦ / В ПВЗ», справа «Передать в доставку». При ПВЗ требуется положительное целое количество коробов; поле появляется плавно, placeholder «Кол-во» виден целиком. При СЦ не должно казаться, будто ограничение «один короб» тоже применяется.

Перед изменением WB — отдельное окно подтверждения с направлением и количеством коробов. Отмена ничего не меняет.

Сервер сверяет/создаёт транспортные короба WB, сохраняет метаданные передачи и не дублирует уже созданные короба при повторе. После передачи запрашивает стикер поставки для СЦ или стикеры коробов для ПВЗ и отправляет их сохранённому агенту.

Исправление автоматической печати после передачи **уже опубликовано** в более раннем релизе `20261110-shipping-labels-v1` и сохранено в последующих. Для закрытой поставки есть повтор этикеток без повторной передачи в доставку. Этикетки валидируются как PNG и кешируются отдельно от списка поставок. Сбой агента не должен повторять саму отгрузку.

Тесты использовали mock WB и принтер. Физический выход бумаги не подтверждался автоматическими проверками.

## 16. Список поставок

Нужны реальные несколько поставок и история. Одна строка содержит поставку, один склад, **«Создана»**, **«Передана»**, число заказов без КИЗ и с КИЗ отдельно, число коробов, куда отгружено, статус. Дата/время по МСК там, где это объявлено интерфейсом.

Название открытой поставки кликабельно. Статус «На сборке» тоже может быть понятным действием перехода, а не неразличимой серой подписью. Отдельную кнопку «Открыть» пользователь удалил.

Фильтр дат — собственный календарь выбора диапазона: первый клик начало, второй конец, предварительная подсветка при движении мыши. Сброс внутри календаря, как в учёте. Не два отдельных нативных поля дат. Фильтрация по дате передачи; это уточнение не надо писать в подписи фильтра. Склад ограничен текущими правами; для единственного делегированного склада избыточный выбор убрать.

## 17. Остатки — последняя реализованная функция

**Сделано в новой серверной версии и опубликовано в `20261110-stocks-v1`.**

WB Content даёт карточки, варианты размеров и все баркоды; WB Marketplace даёт остатки выбранного склада. Используются **chrtId/chrtIds**, не устаревшая схема запросов только по skus.

- Content: `/content/v2/get/cards/list`, курсорная загрузка по 100.
- Остатки: POST `/api/v3/stocks/{warehouseId}`, `{ chrtIds: [...] }`, до 1000.
- Обновление количества: PUT того же endpoint, `{ stocks: [{ chrtId, amount }] }`.
- После изменения выполняется чтение WB и сравнение количества, а не ложный успех сразу после 204.

API собственного сервера:

```text
GET  /api/stores/:id/stocks
POST /api/stores/:id/stocks/sync
POST /api/stores/:id/stocks/:chrtId
GET  /api/stores/:id/stocks-export
```

Снимок публикуется после полного успешного получения данных. Частичный/неуспешный ответ не стирает предыдущий. Пропущенное WB количество — **неизвестно/null**, а не ноль. Карточки обновляются пакетами в БД; placement при синхронизации сохраняется.

Ячейка/адрес — локальное размещение в Supplyo, связанное с магазином, складом и chrtId. Количество — реальный остаток WB, его редактирование вызывает изменение в WB. Нельзя тестировать такой PUT на реальных товарах без задачи пользователя.

Права: чтение через активную ВМС/назначение сотрудника с view, изменение дополнительно требует stocks. Все GET/POST/экспорт ограничены warehouse grant, отзывом и подпиской. Проверяются версия/конфликты; на магазин есть сериализация изменений.

Есть постоянная очередь загрузки, worker, кеш около 5 минут при использовании экрана, ручной cooldown 10 секунд, при 429 отложенный повтор не менее минуты/с учётом заголовков. Frontend опрашивает свой API, видимую вкладку, с отменой устаревших запросов; это не запрос к WB при каждой букве поиска.

Интерфейс:

- Товар/размер, все баркоды, ячейка, адрес, остаток.
- Первый баркод крупнее, дополнительные меньше, без слов «Основной/Дополнительный».
- Поиск, «В наличии / Все товары», разрешённый склад, CSV.
- Пагинация по 100; поиск по товарам, артикулу, размеру, всем баркодам и размещению.
- Общий остаток и число позиций в наличии считаются по всему выбранному складу независимо от поиска и фильтра наличия.
- Поля редактируются непосредственно по клику, без отдельной общей кнопки-карандаша. Ввод имеет одинаковые размеры до/во время редактирования; количество шире, единица «шт.» фиксирована снаружи.
- Enter/blur сохраняют, Escape отменяет; сообщения о результате справа снизу.
- Ровная сетка, подсветка всей строки, серая нижняя полоса без счётчика «Показано».
- Модуль загружается лениво; переключение кабинета сбрасывает состояние старой области, предотвращает гонки ответов.

## 18. Учёт, выполненные работы, зарплата и счета

Серверная обвязка workspace и опубликованные формы есть. Это большой модуль, перенесённый из прототипа; при дальнейших изменениях проверять end-to-end конкретный сценарий, а не считать все старые UI-действия доказанной внешней бухгалтерской интеграцией.

Действующие продуктовые требования:

- Учёт ведётся **по каждому физическому складу отдельно**, выбор склада в верхней панели в стиле выбора кабинета ВМС.
- Вкладки: «Доходы и расходы», «Работы сотрудников», «Зарплата», «Счета».
- По умолчанию текущий месяц. В календаре учёта переключение месяца сразу выбирает весь месяц; затем можно задать свой интервал.
- Карточки «Доходы», «Расходы», **«Прибыль»**. Их меняют склад и период, но **не фильтр вида операции и не поиск**.
- В таблице операций вид операции стоит вторым после даты. Есть фильтр по видам.
- Категории: услуги фулфилмента, оплата материалов, зарплата, аренда, хранение, другое и т.п.
- При добавлении дохода/расхода можно прикрепить документы, счёт, фото/файл оплаты.
- Календарь записи оформлен так же, как остальные, не нативный другой вид.
- Выполненные работы: выбрать добавленного сотрудника склада, а не произвольное свободное ФИО. За день у него может быть **список разных работ** с количеством, ставкой и итогом.
- Выплата переводит работу из списка «К выплате». Выплаты одного сотрудника за один день объединяются в одну расходную операцию, сохраняя детализацию.
- Счёт: дата, номер, вид операции, описание, контрагент, сумма, срок, документы.
- «Отметить оплату» обязательно просит прикрепить фото/файл чека. После подтверждения появляется доходная операция с суммой, контрагентом, категорией и документом, а счёт исчезает из списка неоплаченных.
- Удалять можно все операции, в том числе связанные с зарплатами/счетами, с согласованным обновлением связанного источника, без противоречивых итогов и дублей.
- В подтверждении удаления показывать описание **и контрагента**.
- Удалено нижнее пояснение про localStorage, внутренние записи и неподключённый сервер. Отсутствие текста не означает наличие платёжной/юридической интеграции.

## 20. Лимиты и оптимизация API

Пользователь отдельно настаивал: один персональный WB-ключ на кабинет; фраза «у каждой задачи уникальный ключ» означает **внутренний job/idempotency ID**, а не выдачу отдельного API-токена на каждый вид работы.

Планировщик должен:

- разделять магазины/продавцов и группы методов, соблюдать актуальные лимиты WB;
- использовать общую сериализацию/паузы на токен и учитывать `429`, `Retry-After`, `X-Ratelimit-Retry`;
- объединять одинаковые запросы и не запускать обновления из нескольких вкладок параллельно;
- запрашивать данные только нужных заказов/выбранной поставки там, где endpoint WB это позволяет;
- запрашивать стикеры пачками, проверять КИЗ нужных заказов, кешировать результаты;
- хранить прогресс и повтор в базе, переживать рестарт;
- не уничтожать успешный снимок, когда WB временно недоступен;
- не обещать бесконечную скорость: задержки очереди/маркетплейса должны быть видимы.

Текущая реализация имеет консервативный общий scheduler на токен и обработку backoff. Это не доказательство завершённого распределённого limiter для всех будущих категорий WB/Ozon. При добавлении/изменении API **проверять официальную актуальную документацию**, особенно контракты, статусы и лимиты, а не переносить знания из старого PHP. Для последней работы по остаткам официальная документация item-management была доступна через `dev.wildberries.kg`; `.ru` в том окружении отвечал 498.
