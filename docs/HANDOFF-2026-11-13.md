## Что делаем

supply — работающая WMS для продавцов WB/Ozon, фулфилментов и сотрудников. Путь: вход → магазин/склад → новые заказы → поставка → подбор/сканирование → КИЗ при необходимости → этикетка → передача в доставку. ## Права, данные, безопасность

Один человек может быть владельцем магазинов, фф и сотрудником одновременно. Права определяются сервером для конкретного магазина/склада/связи, а не email или глобальной ролью. Сотрудникам нужна действующая подписка работодателя, собственная не обязательна. Отзыв доступа должен действительно блокировать действия. Не давать новые магазины автоматически всем сотрудникам.

Свой API можно добавить без подписки, но это не открывает всю самостоятельную WMS. Клиент выдаёт доступ конкретному складу фф. Ключи шифруются AES-GCM, не возвращаются браузеру. Сессии HttpOnly/Secure, пароли scrypt, проверки Origin/клиентского заголовка и rate limit. Workspace хранится серверно с optimistic version, вложения в БД.

Удаление магазина сохраняет закрытую историю согласно существующей реализации. Повторное добавление/замена ключа проверяет идентичность продавца. Не удалять таблицы и не переносить клиентские данные между аккаунтами для обхода ошибки.

## WB: важнейшие договорённости

1. Реальные FBS операции; фиксированные лимиты WB, 429/backoff и сохранённая очередь. Повторные запросы сотрудников одного кабинета объединены. КИЗ запрашиваются только ожидающие, пачками до 100, с периодом 15 секунд и защитой от конкурентных записей.
2. Обновление заказов раз в минуту на фоне без шумных уведомлений. Ручная кнопка обходит только периодическую минутную паузу, но не запрет WB 429.
3. Внешние поставки WB импортируются; можно собирать и переносить выбранные заказы в существующую либо новую совместимую поставку. Склады/права/открытость проверяются; готовность и история не теряются при подтверждённом переносе. Не повторять вслепую неопределённые upstream-операции.
4. В сборке колонки: статус, номер заказа, товар, адрес, код, баркоды, стикер текстом WB, действия. Код — бывшее название «ячейка». В новых заказах размещения показывать не просили. Сортировка по естественному адресу, затем баркоду/номеру: одинаковые товары рядом, числовые части 2 до 10. Без адреса группировать по баркоду.
5. Повторный скан одинакового товара выбирает следующий ненапечатанный заказ. Напечатанные «Проверяется»/ошибочные не перехватывают следующий скан. Намеренная повторная печать отдельным действием.
6. Фокус сканера возвращается после действий/диалогов; ввод других форм и поиска не перехватывать. Пустой поиск отпускает фокус после 4 секунд. Русская физическая раскладка сканера переводится в US, GS/F8/Ctrl+] и границы AI восстанавливаются структурно, не портить серийный/криптографический хвост.
7. `sgtin` в requiredMeta ИЛИ optionalMeta означает запрос КИЗ. Неизвестные требования не равны отсутствию маркировки. Структурно валидный КИЗ позволяет сразу печатать, проверка WB асинхронна.
8. Ready для маркированного заказа требует сохранённого КИЗ, подтверждённой печати и разрешающего решения WB. **`filled` («добавили маркировку без проверки») теперь считается разрешающим** по явному требованию пользователя. Не возвращать старый запрет из handoff 10 ноября.
9. Исправление 12 ноября: импорт метаданных не должен превращать optional `customsDeclaration` в обязательную маркировку. `wbMetaVersion:1`, нормализация customs_declaration, учёт decision и ремонт legacy снимков через штатную очередь. Это была причина отказа печатать обычные товары. Нельзя обходить действительно неизвестные/обязательные требования.
10. Auto по умолчанию выключен. Включённый Auto собирает все совпадающие явно немаркированные ещё ненапечатанные позиции выбранной поставки, подготавливает стикеры WB пачками ≤100 и создаёт одно неизменяемое пакетное задание. Стабильный job/body/device/printer не допускают дубль при повторном Enter/потере ack. Новая намеренная печать — новый ID.
11. Готовность всей поставки, а не текущего фильтра, разрешает доставку. СЦ/ПВЗ, число коробов для ПВЗ, отдельное подтверждение. После отгрузки печатается этикетка поставки/коробов. Ошибка принтера не должна повторять отгрузку.
12. Остатки: WB Content + chrtId/chrtIds Marketplace, размер/все баркоды, локальный код/адрес, серверная запись количества с readback и проверкой области. Локальные размещения уже внесены из клиентских таблиц; заново импортировать или стирать их не нужно.

## Ozon — реализовано и границы

Магазин подключается Client ID/API key, зашифрованная отдельная пара, marketplace discriminator. Очередь на Client ID, таймаут/429/backoff, точные int64 через Node 24 JSON source/rawJSON. Не отправлять Ozon credentials в WB и не смешивать worker/state/UI.

Склады `/v2/warehouse/list`, FBS postings `/v4/posting/fbs/list`, пагинация/изменения статуса, снимки в ozon_postings. Карточки `/v4/product/info/attributes`: атрибут 23536, TN VED 22232, баркоды, cached evidence. Пользователь **запретил видимые подписи** «нужна/не нужна маркировка», TN VED и прочие технические объяснения. Как в WB: скан → при необходимости запросить КИЗ. Свежие требования экземпляров Ozon имеют приоритет над карточкой.

Сборка отдельно в ozon-assembly: резерв каждой SKU/ordinal на 2 минуты, следующий экземпляр для дубля, КИЗ сохраняется в Ozon через exemplar create-or-get/set, полный набор экземпляров сохраняет чужие поля, status polling. HTTP 200 на set не означает прохождение. Durable очередь, lost-response reconcile, отзыв прав, защита повторов, ошибки/429. Finish отдельным подтверждением при всех ready, свежей проверке и одной упаковке через `/v4/posting/fbs/ship`; неопределённый ответ сначала сверяется, не повторяется вслепую. Multi-box пока завершать в кабинете Ozon.

Этикетки после awaiting_deliver: `/v3/posting/fbs/package-label/create`, `/v2/posting/fbs/package-label/get`, постоянная очередь/polling, small_label предпочтительно, 45 секунд после локальной упаковки. PDF только с разрешённых Ozon HTTPS хостов, без передачи credentials; лимиты/проверка файла, Poppler в приватном tmp, точные размеры cropbox/rotation. Кеш изображения, immutable print job/device/printer, retry не печатает повторно; новая повторная печать требует подтверждения. Серверная отметка generated/printed_count не доказывает физическую бумагу.

На последнем production-аудите было 4 WB-магазина, 0 Ozon. Ozon контрактные, серверные, browser/native проверки пройдены на фикстурах; реальная Ozon-сборка/этикетка и реальная бумага не проверены. Не выдавать эти ограничения за готовую приёмку. Остатки/мобильная сборка Ozon пока не реализованы.

## Публикация и правила работы

Проверки → сборка → свежий pg_dump+ключ → новый уникальный release → SHA256 загрузок → атомарное current → restart → local/public health и assets → guarded rollback. Не перезаписывать старый release и не заменять production DB тестовой. node_modules symlink указывать на realpath, не на цепочку релизов (уже был отказ разрешения модулей). Безопасные доступы восстановить из личного архива, не из потерянной истории чата.

Старые `.deploy` helpers содержали machine-specific loaders, которые читали прошлые Codex sessions. Они сохранены в личном архиве, не являются переносимой системой деплоя. Не запускать старый prepare повторно с уже занятым именем релиза. Действующий сервер не требует redeploy для восстановления Windows.

Пользователь хочет конкретное завершение работы и публикацию, когда просит. Не просить повторное разрешение на уже разрешённые действия. Сообщать кратко, что изменено, что реально проверено и опубликовано, ограничения. Не делать реальные печать/отгрузку/перенос/изменение остатков ради тестов. Не печатать секреты или реальные коды маркировки в лог.

Открыто: реальный биллинг; production email/recovery и мониторинг требуют отдельного аудита; внешний автоматический backup; подписанный агент с управляемым автозапуском; реальная Ozon-приёмка; Ozon stocks/mobile и multi-box.
